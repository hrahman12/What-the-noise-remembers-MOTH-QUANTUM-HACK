How to play

You are at the loom
  1. Turn the noise dial. Each notch replays a real tamagotchi-v1 job. The gauge on the loom follows it.
  2. Weave from the top, or drag through the picks, and switch between the threads as read and after correction. Watch the shuttle, the sparks and the inspector's flags, and switch the loom sound on to hear each pick.
  3. Click any block: the inspector rides up and reads its syndrome, and the block inspector shows its seven threads.
  4. Load your own image. It's woven in your browser from the engine's recorded rates. Change the width to re-weave the moth or your image.
  5. Copy the WIF 1.1 draft and open it in any weaving program.
  6. Read the chart in The data, or switch the stage to Data to watch it beside the dial.

The data · Logical vs physical

12 grid jobs, 1,792 data qubits each

When does the code earn its keep?

Every point is a completed tamagotchi-v1 job: 256 Steane blocks (1,792 data qubits) under noise p. Filled points ran one syndrome-extraction round; hollow points skipped it. Below the diagonal, a coded bit fails less often than the physical noise rate p. When only the stored thread is noisy, every filled point sits below it, so the code helps. When every gate is noisy too, every point sits above it. This round isn't fault tolerant, so its own gates and ancilla readouts add more errors than the round removes.

The science

Steane 1996 · Hamming 1950
Why weave a quantum code?

Jacquard looms read punched cards: one hole per lifted thread, one card per pick. Babbage later borrowed those cards for his Analytical Engine. Here a loom reads a quantum error-correcting code instead. Ada Lovelace compared that engine to a Jacquard loom weaving flowers and leaves, and the weaver moth is named for her.

The Steane code (Steane, 1996) spreads one logical qubit over seven physical ones. Its bit-flip checks are the three parity checks of the classical [7,4] Hamming code (Hamming, 1950). A single flipped thread gives a 3-bit syndrome that spells out the thread's number in binary. That's the red stitch, and the decoder flips that thread back. The inspector silkworm is named for him.

Two flips in one block fool the decoder. It “corrects” the wrong thread, and the pixel comes out inverted. That's a logical error, and it's what the engine counts. The inspector can't see it either: its syndrome looks normal.

How it was made

30 real Atlas jobs · Aer stabilizer simulator
What the quantum engine did

Atlas tamagotchi-v1 builds a Qiskit circuit on a CSS code (Steane), runs it on the Aer stabilizer simulator under a noise model, and reports how often each logical qubit ends up in the expected state. For every notch of the dial, one job stored 256 logical bits (X on every odd-indexed logical, so 0s and 1s side by side), ran one syndrome-extraction round with in-circuit correction, and read them out. A twin job skipped the syndrome round. Each grid job ran 64 shots, which gives 16,384 block samples per job.

In both profiles the twin without a syndrome round failed less often. It skips the round's idle step and its noisy ancilla readouts, and the engine's final readout is Hamming-decoded anyway: a probe with readout noise only gave 15 errors in 8,000 shots, about 21p², not 7p. One round of extraction only pays off if errors pile up between rounds, and these jobs store each bit for a single step.

Physical qubits: 7 data qubits per logical, so 1,792 per grid job. The engine also uses ancilla qubits to measure the stabilizers, but it doesn't document how many, so they aren't counted here. The size ladder below shows how far one job stretched.

The loom then works classically. It samples each pixel's events from three measured numbers: the logical error rate for a stored 0, the same for a stored 1, and syndrome events per block. The engine counts bit-flip and phase-flip syndromes separately. A probe at readout noise 0.5 gave 1.757 events per block, against 2 × (1 − 0.5³) = 1.75. So a red stitch is drawn at half the measured rate. The draws use a seeded mulberry32 generator, so the page and the Python CLI weave the same cloth from the same seed.

What this does not claim

Simulated, not hardware

No circuit runs per pixel, and no quantum hardware was used. The engine returns aggregate counts, not per-shot records. So the loom draws each pixel's syndrome event and logical flip independently from the measured marginal rates, which drops the real correlation between them. The engine counts bit-flip and phase-flip syndromes as separate events. The loom draws bit-flip syndromes at half that count, which assumes both types are equally likely. That assumption is ours, not an engine output. Which thread flipped is drawn uniformly, because the engine doesn't report it. “Plain codewords” shows 0000000/1111111 so you can see the picture. A real Z readout returns any of the 8 codewords in the right coset, and you can switch to that view. Your own image never leaves your browser, and no new job runs for it.

This circuit's syndrome round isn't fault tolerant. Under noise on every gate it makes things worse at all three noise levels here. That's a real result from the jobs, not a flaw in the weave.

The loom scene is an illustration, not a picture of the circuit. Its sparks, flags, heddle lifts and punch cards replay this cloth's sampled draws, and Ada's cheer or sigh follows the measured verdict (logical flip rate below or above p). The grey fizz on the machinery or on the warp only marks where the chosen profile puts noise; it isn't a count.
